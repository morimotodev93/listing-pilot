# バックアップと復元

## v0.1.1／Schema v5 → v0.2.0／Schema v6 更新前の手順（Phase 6.1追記）

2026-11-21時点の開発ソースは表示版0.1.1／Schema v6で、今回v0.2.0へのバージョン変更はしていません。
以下は次回更新に向けた現行手順です。下部のPhase 4.1／Schema v3の手順と記録は当時の履歴として残します。
**更新版の初回起動前に、全アプリを終了してDBとmedia全体を一組でバックアップしてください。**

1. インストール済み版・開発版を含む全Listing Pilotを正常終了し、プロセスが残っていないことを確認します。
   通常識別子の開発版も同じデータを移行するため、バックアップ前に起動しません。
2. 保存先を確認し、新しい空のバックアップ先を用意します。DBと`media/`全体を、同じ停止期間に一組でコピーします。
   `media/originals/`だけでなく、`media/quarantine/`（`deleted/`を含む）、`.staging/`、`.lock`などの隠しファイルも保全します。
   隔離画像を不要として省略・削除したり、バックアップを既存セットへ混在させたりしません。
3. `listing-pilot.sqlite3-wal`、`-shm`、`-journal`等が存在する場合も同時点の組に含め、元から削除しません。
   異常終了やプロセス終了不明のセットは、そのまま保全した上で隔離コピーを検査します。残存関連ファイルを消して整合性検査を通すことは禁止です。
4. コピー元と先の全ファイルの相対パス・件数・合計サイズ・個別サイズ・SHA-256を照合します。
   停止状態を保ち、日時・アプリ版・schema版・対象領域・結果を記録します。DBだけ／mediaだけの一致を完成扱いにしません。
5. バックアップを直接開かず、新しい空の隔離復元先へ一組をコピーし、同じmanifestを照合します。
   SQLite関連ファイルを別セットと混ぜず、通常データへ上書きしません。
6. 起動**前**に、専用Windowsユーザー／VM等で保存先が隔離されていることを確認します。
   `app.appDirectoriesOverride`を使う専用ビルドでは設定と解決先を先に検証します。EXEを別フォルダーへ置くだけでは隔離されません。
   コピー上で移行前の`user_version=5`、`integrity_check=ok`、`foreign_key_check=0行`を確認し、
   現行版の初回起動で6になること、商品・文章・項目／グループ／値・画像順と原本／隔離のハッシュが保持されることを確認します。
   GUI画像表示と正常終了・再起動も確認し、コピー検証／SQLite・サービス復元／GUI検証を分けて記録します。

**Schema v6へ移行したDBをv0.1.1へ戻すことは保証しません。`PRAGMA user_version`だけを5へ戻す方法は禁止です。**
旧版へ戻す場合は全アプリを止め、移行後のDB・関連ファイル・media全体も別セットで退避してから、
更新前に取得したv5のDB・関連ファイル・media全体を一組で復元します。移行後の変更は更新前バックアップには含まれません。
まず専用環境で復元を検証し、通常領域への復元や実データコピー試験は別途ユーザーの明示承認を得ます。
逆Migration、自動バックアップ、アプリ内復元はありません。

Phase 6.1では新規合成データだけで、8ファイル・102,928 bytesのv5一式をバックアップ→隔離復元→v6移行し、
全ファイル照合・SQLite整合性・全旧データと原本／隔離保持・サービス再起動を確認しました。
GUI・実インストーラー・実データ・残存WAL等のリカバリーはこの試験に含みません。
通常LocalDataは一切アクセスしていません。詳細は[Phase 6.1監査](phase61-release-audit.md)を参照してください。

## Phase 4.1時点の手順・履歴（以下は保存）

対象はListing Pilot 0.1.0 / DBスキーマバージョン3（Phase 4.1）です。
自動バックアップ、アプリ内復元、隔離画像の復元UIはありません。
本手順の検証範囲・未検証事項は [検証記録](verification.md) を参照してください。

Phase 4.1の初回起動はスキーマ0・1・2を3へ自動移行します。**起動前に全アプリを終了し、
DB・SQLite関連ファイル・media全体を一組で新しい場所へバックアップしてください。**
共通項目定義と将来の値はDB内にあり、画像とともに保管が必要です。
スキーマ2までの旧版は3を拒否します。同じ表示バージョン0.1.0でもDB互換性を確認してください。
user_versionだけを下げる操作は禁止です。旧版へ戻す際も移行後の一組を退避し、移行前のバックアップを
専用環境で検証してから復元します。自動バックアップ・逆向き移行はありません。

## 保存場所を確認する

通常のWindows版では、次のアプリ専用フォルダーに保存します。

```text
%LOCALAPPDATA%\com.listingpilot.app\
  listing-pilot.sqlite3
  media\
    originals\
    .staging\
    quarantine\
```

エクスプローラーのアドレス欄に `%LOCALAPPDATA%\com.listingpilot.app` を入力できます。
DBは実行ファイルやプロジェクトの隣には保存しません。
開発版と配布版は同じ識別子なら保存先を共有します。すべてのListing Pilotを終了してください。
専用検証ビルドで `appDirectoriesOverride` を指定した場合は別の場所になるため、設定と実際の解決先を確認します。
見つからない場合に空のDBを作ったり、似た名前のフォルダーを初期化したりしないでください。

## バックアップする

1. 取り込み・保存・削除の完了を待ち、すべてのListing Pilotを通常のウィンドウ操作で終了します。
   タスクマネージャーでも `listing-pilot.exe` が残っていないことを確認します。
   別ユーザー・開発ターミナルから起動しているプロセスも対象です。
2. 保存先と空き容量を確認し、日時を付けた新しいバックアップフォルダーを別の場所に作ります。
   アプリの `media/` 内や、既存バックアップへの上書きは避けてください。
3. `listing-pilot.sqlite3` と **`media/` 全体**を同じ停止期間中にコピーします。
   `quarantine/`・`.staging/`・隠しファイルも含め、取り込み元の写真も別途必要に応じて保管します。
   コピー元は移動・削除・変更しません。
4. `listing-pilot.sqlite3-wal`、`listing-pilot.sqlite3-shm`、`listing-pilot.sqlite3-journal` などの関連ファイルが
   残っている場合は、DBと同じ時点の組として一緒にコピーし、元から削除しないでください。
   異常終了直後や終了状態を確認できない場合は、コピーを復元可能と断定しないでください。
   状態を保全したうえで、隔離したコピー上で整合性と起動を確認します。
5. コピー完了後、元と先のファイル一覧・相対パス・件数・サイズを比較します。
   可能なら全ファイルのSHA-256も比較し、検査中もアプリを起動しません。
   途中エラーや不足があればそのバックアップを完成扱いにしないでください。
6. バックアップ日時、アプリ版、DBスキーマ版、コピー元、確認結果を記録して保管します。
   商品情報・写真を含むため、バックアップ先のアクセス権にも注意してください。

DBだけのコピーでは写真を復元できません。`media/` だけでは商品・画像の関連付けと表示順を復元できません。
ファイル一覧・ハッシュの一致はコピーの検証です。復元可能と判断するには、下記の隔離環境への復元、
SQLite検査、画像表示と再起動の確認も必要です。バックアップ記録では「コピー検証済み」「復元検証済み」を分けて記録します。
異なる日時のDBとメディアを混ぜないでください。コピー中の書き込みを防ぐため、アプリ停止が必要です。

## 復元する前に

復元するとバックアップ取得後の商品登録・編集・画像の変更は反映されなくなります。
現在のデータを上書きすると失う危険があります。復元前に必ず現在のDB・関連ファイル・`media/` 全体を
別の退避先へ一組で保存し、元に戻せることを確認してください。

まず専用の検証環境で復元可能か確認します。通常の実行ファイルを作業フォルダーへコピーしただけでは
保存先は隔離されません。本番LocalDataを共有する開発版を検証用に起動することも避けてください。
専用Windowsユーザー・VM、または保存先の隔離を確認した専用ビルドが必要です。
今回のPhase 3.4作業では本番保存先への復元は行いません。

## 一組のデータを復元する

1. 対象環境のすべてのListing Pilotを完全終了し、現在のデータを一組で退避します。
2. 復元先が意図した専用保存先であることを確認します。
   既存データとの混在・上書きを避け、新しい空の復元領域にコピーします。
3. 同じバックアップ内のDB、SQLite関連ファイル、`media/` 全体を元と同じ相対配置にコピーします。
   現在のDBの `-wal` / `-shm` とバックアップのDBを混ぜないでください。
   元のバックアップは検証・起動せず、そのまま保持します。
4. バックアップと復元先の全対象ファイルの一覧・サイズ・SHA-256を比較します。
5. バックアップのスキーマに対応するアプリを使って復元環境を起動し、商品情報、画像プレビュー、画像の表示順とメイン画像、共通項目の名前・型・単位・非表示状態を確認します。
   正常終了・再起動後も保持され、削除済み画像が商品に再登録されていないことを確認します。
6. SQLiteを扱える担当者は、アプリ停止中の専用コピーに対して `PRAGMA integrity_check;` が `ok`、
   `PRAGMA foreign_key_check;` が0行になること、登録画像のファイル・ハッシュが一致することも確認します。

隔離ファイルだけを `originals/` へ移動しても、DBの関連付けは復元されません。
起動時には未参照ファイルが再び隔離されることがあります。SQLの直接編集で関連付けを作り直す方法は本手順に含みません。
欠落・破損・起動エラーを発見したらバックアップと退避データを保持し、初期化・DB削除で解決しないでください。

将来版で更新されたDBを旧版へ戻すダウングレードは対象外です。
バージョンが異なる場合は移行手順を確認し、元のバックアップを保持した隔離環境で先に検証してください。
このコピー手順は実際の電源断・ディスク故障で失われたデータの回復を保証するものではありません。
