# 0006: 共通カスタム商品項目の定義管理

- 日付：2026-11-12（日本時間）
- 状態：採用・Phase 4.1実装

## 決定

B方式として、商品から独立した共通項目定義を `attribute_definitions` に保存する。
`products` の列は追加せず、商品別の任意項目やジャンル別セットは導入しない。
定義はRust生成UUID v4で識別し、名前変更でもUUID・作成日時・型・単位を保持する。

型はText（`text`）とNumber（`number`）だけとし、作成後の型変更APIは設けない。
Numberだけ任意の単位を作成時に設定でき、空欄はNULL。単位変更APIも設けない。
名前はRustのtrim後1〜80 Unicode文字、単位は最大20文字で、制御文字・改行は拒否する。
Unicode正規化・全角半角変換はせず、BINARY一意制約により非表示の名前も再利用できない。

非表示は `archived_at` の設定、復元はNULLへの変更とする。物理削除APIを作らず、
定義と将来の登録値を保持する。全定義を取得し、Reactで非表示項目の表示を切り替える。
一覧は通常項目を先に、同じ状態では作成日時・UUID順にする。

名前変更・非表示・復元はIDと `expectedUpdatedAt` を条件とする単一UPDATEで行う。
0件更新は不在と競合を区別し、UTC日時は前回+1ns以上に進める。
競合を自動再試行せず、UIは入力を保持して保存を停止し、利用者に一覧の再読み込みを案内する。

## 値テーブルと商品削除

`product_attribute_values` は `(product_id, attribute_id)` を主キーとし、
商品と定義の双方をON DELETE RESTRICTで参照する。空白だけの値をCHECKで拒否する。
未入力は行なしで表し、将来のNumber値も精度保持のため十進数文字列としてTEXTに保存する。
Phase 4.1には値の登録・編集IPCも商品別入力UIも作らない。

通常は値テーブルが空なので商品削除は従来どおり動作する。
値がある場合、既存の商品削除トランザクションは外部キー違反で全件をロールバックし、
商品・画像・値と画像ファイルを保持する。外部キー無効化やCASCADEは導入しない。
Phase 4.2で値入力を公開するとき、削除確認・最新値の再検証・値削除を既存の安全な
トランザクションに組み込む。現時点でその削除動作を先行実装しない。

## 移行と互換性

0001・0002を変更せず、0003で2テーブルを追加してスキーマ3へ順次移行する。
既存のIMMEDIATE内で適用し、途中失敗はスキーマ・user_versionごと戻す。
3の再適用はデータを変更せず、4以上の未知のスキーマは初期化エラーとして保持する。
既存商品・画像の自動変換、保存場所・識別子・CSP・権限・メディアロックの変更はない。

スキーマ2までの旧版は3を開けない。アプリの表示バージョンが同じ0.1.0でも互換とは限らない。
移行前に全アプリを終了し、DB・関連ファイル・`media/` 全体を一組で別途バックアップする。
自動バックアップ・逆向き移行は実装しない。旧版へ戻す場合は移行前の一組を隔離環境で検証し、
移行後のデータを退避した上で復元手順を適用する。user_versionだけを戻してはならない。

実施した検証と限界は [検証記録](../verification.md)、手順は [バックアップと復元](../backup-and-restore.md) を参照。
