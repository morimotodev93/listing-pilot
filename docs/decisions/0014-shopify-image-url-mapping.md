# 0014: Shopify画像URLの管理と画像付き商品CSV出力

- 日付：2026-11-19（日本時間）
- 状態：**提案・Phase 5.2.1（設計）**。このADRを作成する時点でアプリの実装・DB変更は行わない。
- 関連：ADR 0010（汎用単品出力）、0012（汎用一括出力）、0013（Shopify画像なしCSV）
- 実装の基準：`c01cc1d`（Phase 5.1完了コミット）

## 背景・検証結果

Listing PilotはローカルのJPEG/PNG/WebP原本を画像UUID・商品UUID・`sort_order`・SHA-256で管理し、Shopify用には現状10列・画像なしの商品CSVを生成する。Shopify商品CSVにローカルファイルパスを指定しても画像は取り込めないため、公開HTTPS画像URLとの対応付けが必要である。

Phase 5.2.0では青い小皿の4画像をShopify Filesに手動アップロードし、得られた `cdn.shopify.com` のURLを使った新規商品向けCSVを検証した。

- **テストA：画像1枚**の商品登録に成功し、画像が表示された。
- **テストB：画像4枚**の商品登録に成功し、正面・上面・側面・裏面の4枚が期待した順に表示された。1枚目がメイン画像だった。
- 下書き状態の新規商品に対する検証である。**画像URLの長期的な有効性、altテキストの再エクスポート値、同一Handleの再取込・既存画像更新、Shopify APIでのアップロードは未検証**であり、今回の成功から保証しない。

## 決定1：ローカル画像管理とShopify URL設定を別画面に分ける

- 既存の商品画像画面は、画像の追加・閲覧・並び替え・削除を主目的として維持する。狭いサムネイル欄に長いURL入力欄を並べない。
- 商品画像から **「Shopify画像URLを設定」** を開く。専用ダイアログまたは独立パネルに、画像を現在の`sort_order`順で縦に列挙する。
- 各行にサムネイル、画像順序、短い識別情報、フル幅のURL入力欄、設定状態を表示する。必要に応じて任意の画像altテキスト入力欄を設ける（自動推測はしない）。
- **一括貼り付け**を提供する。1行1URLを現在の画像順に対応させ、件数・空欄・形式を検査した結果と対応サムネイルを確認してから一括適用する。件数不一致やエラーで既存設定を部分更新しない。
- 入力欄は空欄（未設定）を許す。未設定は明示表示し、保存前の編集内容を黙って破棄しない。保存完了・競合・失敗を区別して表示する。
- URLの対応は画像の表示番号ではなく**不変の画像UUID**で保持する。画像を並び替えてもURLとaltテキストは画像に追従し、CSVの`Image position`だけを再計算する。

## 決定2：外部URLをローカルSQLiteで画像・ストア別に保持する

- `product_images`にShopify固有のURL列を追加せず、画像UUIDを参照する**別テーブル**を設ける。Shopify以外の販売先や複数ストアを区別できるよう、`platform`と`store_key`を含める。
- `store_key`は利用者が指定した対象ストアの正規化された`*.myshopify.com`ドメイン等、再現可能な識別子とする。現段階では認証やShopify API連携は行わない。異なるストアのURLを暗黙に混用しない。
- 最小の概念モデル：`image_id`、`platform`、`store_key`、`url`、`image_sha256`、任意の`alt_text`、更新時刻。主キーは `(image_id, platform, store_key)`。`image_sha256`は登録時点の管理原本のハッシュを記録し、出力時に現在の画像メタデータと照合する。
- このハッシュの一致が**Shopify CDN上の画像内容まで同一と証明するわけではない**。手動アップロードしたURLが対象画像を指すかは、設定時のサムネイル照合と利用者確認で担保する。
- 新スキーマは**既存Schema v5からの番号付き・前進のみのMigration 0006（想定）**で追加する。既存0001〜0005を書き換えず、既存の商品・画像・カスタム属性を保持し、失敗時はトランザクション全体を戻す。`foreign_key_check`と旧データ保持テストを必須とする。
- 画像削除・商品削除時の参照整合性も明示的に実装する。既存削除が画像行を削除できなくなる状態を作らない。関連URL行の扱い（明示削除／FK動作）は、既存の保護・失敗時復旧契約と合わせて実装レビュー時に確定し、テストする。画像原本や他商品のURLを削除・更新してはならない。
- DBと`media/`を一組としてバックアップする既存原則を維持する。URL情報は機密情報に準じて扱い、不必要にログへ出さない。

## 決定3：公開画像URLの入力・保存の安全性

- Phase 5.2.2の初期対象は**Shopify Filesからコピーした公開HTTPS URL**とし、URLの構文をRustで検証する。少なくとも `https://`、ホスト名の厳密な比較、ユーザー情報の禁止、制御文字の拒否、合理的な最大長、画像ごとの重複URLの検出を行う。`cdn.shopify.com`だけを対象にするか、他のHTTPS画像ホストも許すかは実装前に検証・確定する。
- **URL形式の検証と実在・画像内容の検証は別**。初期版はShopifyへのネットワークリクエスト、リモート画像のダウンロード、HTTP HEAD確認を行わない。「形式OK」を「Shopifyで取得可能」と表示しない。
- ローカル画像ファイルの絶対パス、`file:`、`data:`、スクリプトURL、管理画面の認証付きURLは受け付けない。URL入力を理由にCSP、Asset Protocol、Tauri capabilitiesを広げない。
- 複数ストアのURLや間違った画像の貼付けは利用者が識別できるよう、**ストア名と画像サムネイルを保存前・出力前に明示**する。

## 決定4：Shopify CSVは「画像なし」と「画像URL付き」の二方式

- **画像なし**：Phase 5.1の10列、1商品1行、`shopify-products.csv`、既存IPC・確認と出力契約を維持する。URL未設定でも使用できる。
- **画像URL付き**：既存10列の末尾に次の3列を追加した**13列**の新規商品登録用CSVを生成する。

```csv
Product image URL,Image position,Image alt text
```

- 画像1枚につきCSV1行。最初の行は商品情報＋1枚目の画像URL・位置1、2枚目以降は同じ`URL handle`と各画像URL・位置・altを記載し、商品基本情報欄は空欄にする。商品を跨ぐ行順と各画像の順序は決定的にする。
- 画像順は現在の `sort_order` に従い、`Image position`を**1始まり**で生成する。画像UUIDとURLの関係は並び替え後も維持する。初期版ではバリエーション画像、画像削除・既存Shopify商品の更新を扱わない。
- 画像URL付きモードでは、対象各商品について画像が1枚以上あり、**その商品の全管理画像に選択ストア向けの有効なURLが設定済み**であることを条件とする。未設定・重複・不正URL・SHA不一致があれば対象商品を明示し、**全件出力を停止**する。黙って画像を飛ばしたり、部分成功させたりしない。
- altテキスト未設定は空欄（必要なら明示警告）とし、画像ファイル名・管理メモから勝手に生成しない。
- Shopify用共通ルールの`draft`／`false`固定、JPYストアの**利用者による明示確認**、SKU・価格・数式検証、15MB未満のUTF-8バイト長検証、UTF-8 BOMなし・LF、CSV引用符エスケープを維持する。
- 出力は**CSVのみ**とし、管理原本をコピーしない。画像なしモードに汎用の200画像・1GiB制約を後付けせず、画像付きでも実際のCSVサイズと採用した商品・画像数制約で判定する。

## 決定5：プレビュー・変更検出と安全な確定

- Shopify画面では選択対象（1〜20商品）のほか、**出力モード・対象ストア・画像の枚数・URL設定状況・メイン画像・画像順序**を確認できるようにする。
- 画像URL付き出力には、モードとストア識別子、画像UUID・現在順序・SHA-256・URL・alt情報を含む**Shopify画像付き専用スナップショットトークン**を設ける。Phase 5.1の画像なしトークンと混用しない。
- プレビューから出力までに商品・画像順・URLマッピング・ストア選択が変われば古い確認を拒否する。警告があればトークンに結び付いた再確認を必須とし、プレビュー再読込・エラー・キャンセル後は承認を失効させる。
- 出力は、事前準備→Rustネイティブの出力先選択→再検証→同一親へのステージングとsync→短いSQLite `IMMEDIATE`で商品およびURL対応の最終照合→`Workspace.finish()`による**1回だけの非置換確定**とする。DB Mutexを長いファイルI/O中に保持しない。
- 元画像・DB・既存の完成出力を上書きしない。通常失敗時は当該処理が作成したファイルだけを限定清掃する。結果不明時は保持する。既存の汎用単品／一括出力の契約を変更しない。
- 既存Handleの上書きをオフにした**新規商品**の検証を基本とする。アプリ単独でShopify上の重複Handleや実際のJPY設定を検知できると主張しない。

## 実装順と受け入れ基準

1. **Phase 5.2.1（今回）**：ADRで決定と未検証条件を記録。コード・DB変更なし。
2. **Phase 5.2.2**：Migration、画像UUID／ストア別URL保存、専用UI、一括貼付けと確認、画像付き13列CSV、既存画像なし10列の維持、関連Rust／Reactテストを実装。
3. **Phase 5.2.3**：隔離DBと実WebView2で保存・再起動・並び替え・画像削除・競合・失敗時保護を検証し、Shopify Dev Storeで画像1枚／4枚のCSVをインポート・再エクスポートする。

最低限のテストは、旧DBからの移行・既存データ保持、画像UUID対応と並び替え、一括貼付けの件数不一致と途中失敗、複数ストア隔離、URL構文と誤紐付け防止、URL/画像メタデータの競合失効、画像なし回帰、13列の行構成・位置・alt、数式リスク・JPY確認、全件失敗時清掃と非置換確定、画像削除・商品削除時の整合性とする。

## 対象外・未確定事項

- 自動アップロード、Shopify Admin API・認証、商品更新／同期、公開状態の変更、CSVによる画像削除、メタフィールド、サイズ・色のバリエーションは対象外。
- URLの有効期限やCDN資産の恒久性は保証しない。Shopify側の画像複製や不要ファイルの掃除も自動化しない。
- **実装前に確定する細部**：許可する画像URLホスト範囲、画像削除時のURL参照行の具体的な削除／保持方針、altテキストの文字数・検証規則、複数ストアの識別UIと保存時の競合処理。
- 配布版・別PC・電源断・Windowsのリポジトリ監視下で起きる最終移動エラー5は本ADRで解決したと扱わない。
